## What we did
- Talked through the cost worry first: the recommender makes **zero OpenAI calls at request time** — it's pgvector math on vectors we already embedded once. text-embedding-3-small is pennies; you can't hit $10/mo with this design. Rule we set: **embed on write, never put an LLM in the request path.**
- **Phase 1 — "hidden gems":** new `tasteCandidates` pulls the most-loved posts of ANY age matching your top categories/authors/tags, merged into the feed pool. Before, the ranker only saw the newest 300, so an old perfect-match was unreachable. Pure SQL, $0.
- **Phase 2 — "Not interested":** a thumbs-down (👎) on For You cards → card vanishes + that genre/author fades (writes a −4 `user_signals` row; `dismissedPostIds` drops it from the feed).
- **Phase 3 — trending trust:** Bayesian small-sample damp (×n/(n+5)) so on a quiet day 3 likes can't outrank a post with 300.

## Important notes & decisions
- **GIN-index catch (remember this):** N101 ALREADY had `posts_tags_gin_idx` from migration **0006** with **jsonb_path_ops**, which supports `@>` only — NOT the `?|` I first wrote in `tasteCandidates`. My new `0022` migration collided on the name. Fix: switched the query from `?|` to the **equivalent `@>`-containment OR** (`tags @> '["x"]'` per tag) — now served by the existing 0006 index — and **reverted my redundant `0022`** (deleted the sql + snapshot, removed the journal entry, reverted the schema line). NB needed its own index (it had none → migration `0019`, jsonb_ops).
- Converted `dismissedPostIds` to **pure Drizzle**; left the heavy queries (computeAffinity, trending recompute, semanticScores, insert-guards) as raw `sql` — Drizzle can't express those, and raw vs builder has **zero** perf cost on Workers+Neon (same wire SQL).
